# 听歌房视频房外壳复刻设计

## 目标

让 `/music/rooms/:roomId` 的外部页面与 `/tools/sync-room/:id` 使用同一套房间外壳：顶部房间信息栏、状态操作、提示条、页面背景、内容宽度和响应式布局保持一致；听歌房内部的 Mineradio 播放、点歌、队列、聊天和实时同步逻辑保持不变。

## 现状与根因

视频房由 `VideoRoomPage` 提供房间外壳，包含退出、房间号复制、控制权限、在线人数、同步状态、重新同步和内容区布局。听歌房的 `MineradioPage` 当前使用全屏沉浸式容器，并且 `AppShell` 会为该路由隐藏站点 Header/Footer，因此两类房间的外部体验不一致。

## 方案

在 `MineradioPage` 中复用视频房的外壳结构和交互语义：

- 使用与视频房相同的页面背景、顶部留白、粘性顶部栏、最大宽度和网格布局。
- 顶部显示退出房间、房间名、房间号复制、控制权限、在线人数、同步状态和重新同步。
- 保留现有 `notice` 提示条。
- Mineradio iframe 继续作为主要内容区，保持现有 `postMessage` 播放适配器和房间同步链路不变。
- 听歌房仍隐藏站点通用 Header/Footer，避免进入房间后出现额外导航；只复刻视频房的房间级外壳。
- 视频房列表继续过滤 `mode: music` 的房间。

## 验收标准

1. 听歌房页面存在与视频房相同的房间级顶部操作区和布局类名。
2. 页面仍加载 `/mineradio/?blue-room=<id>`，并保留原有音乐房测试覆盖。
3. 退出、复制房间号、重新同步、成员数量和同步状态仍来自听歌房自身状态。
4. 观影室不会显示听歌房。
5. 前端测试、代码检查、生产构建通过。
6. 线上 `/music/rooms/<id>`、`/tools/sync-room` 和 `/api/health` 验收通过，并保留上一版静态文件回滚目录。

# 视频房实时同步与生命周期加固设计

## 目标

完善视频房的上传反馈、房主控制、本机同步、成员在线状态和房间自动销毁，使电脑房主的播放状态成为唯一可信来源，并让断线、重连和大文件上传都有可见且可恢复的行为。

## 已确认的产品规则

- 房间处于“仅房主控制”时，只有房主账号可以播放、暂停、拖动进度和调整倍速。
- 手机成员可以观看，但手机浏览器的原生媒体控件不能改变房间状态；误触后播放器立即恢复服务器状态。
- 上传视频显示真实上传百分比、已传大小和失败状态；上传完成后才加入片单。
- “本机同步”不上传视频内容。每台设备各自选择同一个文件，服务端只保存文件名、大小和指纹，不保存本机路径。
- 成员在线状态通过实时心跳更新；断线超过短暂容错窗口后显示离线，重连后恢复在线。
- 房间无人后进入空闲/过期阶段，达到保留期限后软删除并清理房间拥有的媒体文件。

## 范围与约束

本次只改视频房相关前后端和测试，不改变已有的媒体访问授权、视频格式限制、房间数据模型的基本含义，也不引入 Redis 或新的部署服务。保留工作区中已经存在的相关未提交改动，并在其基础上完成闭环。

## 方案

### 1. 上传进度

`useVideoRoom` 为视频上传维护独立的上传状态，包括是否上传中、已传字节数、总字节数和百分比。上传请求使用现有 API 地址和鉴权方式，但通过上传进度回调更新状态；成功后刷新视频会话并清理进度，失败后保留可理解的错误提示并清理忙碌状态。

`VideoRoomSidebar` 在上传入口附近显示进度条、百分比和已传/总大小。上传期间禁用重复选择和其他会改变片单的操作，避免同一个房间同时提交多个媒体变更。

### 2. 房主控制与服务器权威

服务器继续使用 `can_perform_room_action(..., "playback_control")` 作为最终权限判断，事件载荷中的用户身份不参与授权。前端播放器的原生 `play`、`pause`、`seeking` 和 `ratechange` 事件统一经过“远程应用抑制”和“本地权限判断”两层处理：

1. 服务器应用快照触发的媒体事件只更新本地播放器，不再次发送控制事件。
2. 非房主的本地原生操作不发送 `playback_control`，而是用最近一次服务器快照恢复播放状态、进度和倍速，并提示“仅房主可以控制播放”。
3. 房主的原生操作转换成现有版本化控制事件，继续接受服务器版本冲突处理。
4. 自定义播放按钮和进度条仍按 `canControl` 禁用，避免用户误以为可以操作。

房主判断统一按字符串化用户编号比较，兼容登录态和接口返回值类型不同的情况。房主转让、重连和状态刷新后，控制权即时根据最新房间信息重新计算。

### 3. 本机同步

本机同步继续使用浏览器 `File` 对象和指纹校验：

- 房主登记文件时只提交文件名、大小和 SHA-256 采样指纹，并在房主浏览器创建本地播放 URL。
- 其他成员选择文件时先计算指纹；不匹配时不创建播放 URL，并明确提示文件不一致。
- 选择成功后仅通过实时事件上报当前成员、片单项和准备状态；事件不携带本机路径或文件内容。
- 加入房间、重连、切换当前片单项后，客户端重新上报当前项的准备状态，避免进程内状态丢失造成“本机同步不可用”。
- 服务端只在当前进程保留准备状态用于房间内提示；断开连接时清理对应成员状态，重新连接后由客户端重新上报。

本机视频同样遵守房主控制规则：成员设备可以准备并被动播放，但不能通过原生控件改变共享状态。

### 4. 成员在线状态

新增房间级 `presence_heartbeat` 实时事件。客户端在实时连接成功并加入房间后定期发送心跳；页面不可见时暂停发送，恢复可见时立即补发一次。服务端只接受已认证且属于该房间的连接，更新成员的 `last_active_at`，并在在线状态发生变化时向房间广播成员状态。

房间详情和视频房初始化使用全量成员列表，以便同时显示在线和离线成员。前端收到成员加入、离开、在线状态更新或完整成员列表时，按用户编号合并状态，不重复添加成员。

心跳不是播放时间心跳的替代品：播放时间心跳仍只允许房主发送，成员在线心跳只负责 presence 和生命周期。

### 5. 自动销毁

清理任务在判断房间是否无人前，先把 `last_active_at` 超过在线容错窗口的成员标记为离线，并广播必要的状态变化。然后继续使用现有生命周期：

```text
active/idle（无人且超过空闲阈值） -> expired -> deleted（超过保留阈值）
```

软删除保留数据库记录用于排查；删除阶段只清理由系统拥有且位于视频存储根目录内的视频和字幕文件。活跃心跳、重新加入或有效操作会把房间恢复为 active，不会误触发过期清理。

清理逻辑必须在单元测试中使用可注入的当前时间或明确设置历史时间，验证“僵尸在线成员不会阻止过期”和“仍有有效心跳的成员不会被清理”。

## 错误与恢复

- 上传失败：显示服务器返回的中文错误，结束进度条和忙碌状态，允许重新选择文件。
- 上传连接中断：不把半成品加入片单；服务端继续删除未完成的目标文件。
- 播放控制版本冲突：使用现有冲突快照恢复，不重复发送旧控制事件。
- 非房主原生误触：恢复最近服务器状态，并显示权限提示；实时连接不可用时显示同步失败，不假装已操作成功。
- 本机文件不匹配：不广播 ready=true，保留当前可用状态并提示重新选择。
- 心跳或实时连接失败：显示连接恢复状态；页面恢复可见或 Socket 重连后立即重新加入并请求状态。
- 房间已经过期或软删除：现有 API 错误提示和页面离开逻辑继续生效，不在前端缓存中继续操作。

## 代码边界

- 前端视频状态、上传进度、心跳和本机文件恢复：`frontend/src/features/video/useVideoRoom.js`
- 上传入口、进度展示、成员状态和本机同步提示：`frontend/src/features/video/VideoRoomSidebar.jsx`
- 播放器原生事件接线和进度条显示：`frontend/src/features/video/VideoStage.jsx`
- 视频上传请求封装：沿用 `frontend/src/utils/request.js` 的鉴权与请求方式；不改变视频路由路径。
- 实时事件、成员状态、权限和清理：`backend/websocket_server.py`、`backend/sync_room_crud.py`、`backend/room_cleanup_task.py`，必要时调整视频房间详情接口的成员查询。

## 测试设计

### 前端

- 上传请求把进度回调转换为 0 到 100 的状态，并在成功、失败后正确清理。
- 进度条显示百分比和已传大小，上传中禁用重复操作。
- 非房主触发原生播放、暂停、拖动和倍速时不发送控制事件，并恢复到服务器快照。
- 房主的原生控制仍发送版本化事件。
- 本机文件指纹匹配、不匹配、重连重新上报和成员 ready 状态展示。
- 成员加入、离开、离线和重连状态按用户编号正确合并。

### 后端

- 仅房主控制房中，非房主 WebSocket 控制事件被拒绝；全员控制房仍保持原有行为。
- presence 心跳只更新真实成员，广播状态变化，并拒绝伪造房间或非成员请求。
- 超时在线成员先被标记离线，空房随后可以过期；有效心跳不会被标记离线。
- 现有空闲、过期、软删除和媒体文件清理测试继续通过。
- 现有视频路由、视频协议和 WebSocket 安全测试继续通过。

## 验收标准

1. 从电脑选择上传视频时能看到持续变化的百分比，成功后房间内成员都能播放。
2. 手机成员在房主控制模式下点击原生播放或拖动进度，不会改变电脑和房间的播放状态。
3. 本机同步模式下，房主和手机分别选择同一个文件后能被识别为已准备；选择错误文件会被拒绝；重连后状态能恢复。
4. 成员离开、断网、重连时，所有仍在线的页面能在短时间内看到状态变化。
5. 所有成员离开后，房间按既有生命周期进入过期并最终软删除，不会因断线残留的在线标记永久保留。
6. 前端相关测试、后端相关测试、前端构建和项目既有回归命令全部通过。
